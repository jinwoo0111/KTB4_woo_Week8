# 게시글 검색 고도화 기록

이 문서는 게시글 검색 기능을 DB 검색부터 시작해 데이터 증가에 따른 한계를 확인하고,
이후 Elasticsearch 도입을 검토하는 과정을 단계별로 기록한다.

완성된 결과만 남기는 것이 아니라 각 단계에서 내린 결정, 선택 이유, 예상과 실제 결과,
구현 과정에서 발견한 문제와 배운 점을 함께 기록하는 것을 목적으로 한다.

## 진행 원칙과 전체 로드맵

### 0순위 원칙

이 프로젝트에서는 기능의 빠른 완성보다 구현 과정을 이해하고 설명할 수 있는 개인의
성장을 우선한다.

- 완성된 코드를 바로 적용하기 전에 요구사항과 선택 이유를 먼저 이해한다.
- 구현 전에 예상한 동작과 구현 후 확인한 실제 동작을 비교한다.
- 오류와 성능 한계를 감추지 않고 발생 원인과 해결 과정을 기록한다.
- 테스트를 단순한 통과 수단이 아니라 설계한 조건을 검증하는 도구로 사용한다.
- 반복적인 구현은 도움을 받을 수 있지만, 적용된 코드의 역할과 선택 이유를 확인한다.
- 각 단계가 끝날 때 결정 사항, 검증 결과 및 배운 점을 이 문서에 추가한다.
- 각 구현 단위에서 관련 Spring·DB·CS 핵심 개념을 확인하고, 면접이나 기술 질문으로
  다시 설명해보며 이해 여부를 점검한다.
- 새로운 개념이나 중요한 개념이 등장하면 일정이나 분량을 이유로 생략하지 않는다.
  개념의 동작 원리, 현재 작업과의 관계, 선택 가능한 대안 및 한계를 이해한 뒤 다음
  구현으로 진행한다.

브랜치 생성과 Git 인증 등 기능 고도화를 시작하기 위한 준비 과정은 별도의 단계로
기록하지 않는다.

현재 문서와 프로젝트의 범위는 8단계까지다. React 검색 화면은 검색 저장소와 쿼리
구조를 결정한 뒤 진행한다. 7단계에서는 PostgreSQL의 검색 기능으로 현재 H2 기준선을
개선할 수 있는지 먼저 확인하고, 8단계에서는 측정 결과를 근거로 적용 방식을 결정한다.
Elasticsearch는 PostgreSQL만으로 요구사항을 충족하기 어려울 때 성능과 검색 품질뿐
아니라 데이터 동기화와 운영 복잡도까지 비교할 후보로 둔다.

Elasticsearch가 반드시 필요하다는 결론을 측정 전에 정하지 않는다. 측정 결과 현재
규모에서는 DB 검색만으로 충분하다면 그 사실도 그대로 기록한다. 이 경우 다음
프로젝트의 Elasticsearch 도입은 현재 서비스의 필수 해결책으로 과장하지 않고, 검색
품질과 확장 가능성 및 운영 복잡도를 직접 비교하기 위한 학습 목적의 고도화로 정의한다.

React 구현을 뒤로 미룬 이유는 화면을 먼저 완성하기보다 현재 DB 검색의 특성과 한계를
직접 측정하고, 그 결과를 바탕으로 다음 검색 기술을 선택하는 경험에 우선순위를 두기
위해서다.

성능 비교에서는 외부 API인 `GET /posts`의 계약을 유지하고 내부 검색 구현만 교체한다.
H2 결과는 최초 방식의 변화 추세를 관찰하는 기준선으로 사용한다. 검색 방식의 핵심
비교는 동일한 PostgreSQL 환경과 10만 건 데이터에서 기본 `LIKE '%keyword%'`,
`pg_trgm`, Full Text Search를 대상으로 수행한다. 단순 응답 시간뿐 아니라 실행 계획,
처리량, 검색 결과 특성, 인덱스 크기와 쓰기 비용도 함께 확인한다.

단계 번호와 작업 범위가 불분명할 때는 새로운 단계를 임의로 만들지 않고 이 로드맵을
기준으로 현재 위치와 다음 작업을 확인한다. 구현 과정에서 범위 변경이 필요하면 먼저
변경 이유를 검토한 뒤 로드맵을 수정한다.

## 1. 검색 기능 요구사항

### 1.1. 검색 기능 목적

사용자가 게시글이 많아졌을 때 목록을 직접 탐색하지 않고 키워드로 원하는 게시글을
찾을 수 있어야 한다.

첫 번째 버전에서는 DB의 문자열 포함 검색을 이용한다. 이후 게시글 데이터를 늘리면서
응답 시간과 DB 실행 계획을 측정하고 DB 검색의 한계를 직접 확인한다.

### 1.2. 검색 대상

| 검색 범위 | 동작 |
| --- | --- |
| `all` | 제목 또는 내용에 검색어가 포함된 게시글을 검색한다. |
| `title` | 제목에 검색어가 포함된 게시글을 검색한다. |
| `content` | 내용에 검색어가 포함된 게시글을 검색한다. |

- `scope`를 생략하면 `all`을 기본값으로 사용한다.
- `all`은 제목과 내용이 모두 일치해야 한다는 의미가 아니다. 제목 또는 내용 중 하나만
  일치해도 결과에 포함하는 OR 조건이다.
- 제목과 내용이 모두 일치하더라도 같은 게시글은 한 번만 반환한다.
- 작성자 검색은 첫 번째 버전의 범위에서 제외한다.

### 1.3. 검색 일치 방식

DB의 `LIKE '%검색어%'`를 사용해 문자열 포함 검색을 구현한다.

- 영문 검색에서는 대소문자를 구분하지 않는다.
- 오타 교정, 형태소 분석, 동의어 및 관련도 검색은 지원하지 않는다.
- `LIKE` 검색은 첫 번째 DB 검색의 기준선이며, 최종 검색 방식으로 확정한 것은 아니다.

### 1.4. API 경로

검색 전용 API를 만들지 않고 기존 게시글 목록 API에 검색 조건을 추가한다.

```http
GET /posts?keyword=스프링&scope=all&cursor=100&size=10
```

- `keyword`가 없으면 기존 게시글 목록을 조회한다.
- `keyword`가 있으면 조건에 맞는 검색 결과를 조회한다.
- `keyword`가 있고 `scope`가 없으면 `all`을 적용한다.
- `keyword` 없이 `scope`만 전달하면 잘못된 요청으로 처리한다.
- DB 검색에서 Elasticsearch로 내부 구현이 변경되더라도 외부 API 계약은 유지할 수
  있도록 설계한다.

### 1.5. 검색어 공백 처리

- 검색어의 앞뒤 공백은 제거한다.
- 첫 번째 버전에서는 내부 공백을 입력된 형태로 유지한다.
- `keyword`가 전달됐지만 앞뒤 공백 제거 후 빈 문자열이면 `400 Bad Request`를
  반환한다.
- `keyword` 자체가 없으면 검색 요청이 아니라 기존 게시글 목록 조회로 처리한다.

연속된 내부 공백을 하나로 합치면 검색어와 저장된 게시글의 공백 형태가 달라져 오히려
검색되지 않을 수 있다. 내부 공백 정규화나 검색어를 단어별로 분리하는 기능은 이후
개선 단계에서 다시 검토한다.

### 1.6. 대소문자 처리

영문 검색에서는 대소문자를 구분하지 않는다.

예를 들어 게시글에 `Spring Boot`가 있다면 `spring`, `Spring`, `SPRING` 검색이 모두
해당 게시글을 반환해야 한다.

구체적인 DB 쿼리와 인덱스에 미치는 영향은 구현 및 성능 실험 단계에서 확인한다.

### 1.7. 검색어 길이

앞뒤 공백을 제거한 검색어의 길이는 최소 2자, 최대 100자로 제한한다.

- 2자 미만이면 `400 Bad Request`를 반환한다.
- 100자를 초과하면 `400 Bad Request`를 반환한다.
- 한 글자 검색은 너무 많은 결과를 반환할 가능성이 있어 검색 정확도와 DB 부하를
  고려해 첫 번째 버전에서 제외한다.

### 1.8. 특수문자 처리

일반 특수문자는 검색어로 허용한다. `C++`, `C#`, `Spring-Boot`처럼 특수문자가 의미를
가지는 검색어를 일괄적으로 제거하거나 거부하지 않는다.

- `LIKE`에서 와일드카드로 사용되는 `%`, `_`는 일반 문자로 검색한다.
- escape 문자로 사용하는 `\`도 일반 문자로 검색할 수 있도록 처리한다.
- 검색 쿼리는 문자열을 직접 결합하지 않고 파라미터 바인딩을 사용한다.

### 1.9. 결과 정책

- 삭제된 게시글은 검색 결과에서 제외한다.
- 검색 결과는 게시글 ID 내림차순으로 정렬해 최신 게시글부터 반환한다.
- 첫 번째 DB 검색 버전에서는 조회순, 좋아요순, 관련도순 정렬을 지원하지 않는다.
- 기존 게시글 ID 기반 커서 페이지네이션을 유지한다.
- 기본 페이지 크기는 10개이며 최대 페이지 크기도 10개로 제한한다.
- 다음 페이지가 있으면 `has_next`와 `next_cursor`를 반환한다.
- 다음 페이지가 없으면 `has_next`는 `false`, `next_cursor`는 `null`로 반환한다.
- 검색 대상 데이터가 페이지 조회 중 변경되지 않는다면 페이지 사이에 같은 게시글이
  중복되거나 누락되지 않아야 한다.
- 검색어 또는 검색 범위가 변경되면 기존 검색 결과와 커서를 초기화하고 첫 페이지부터
  다시 조회한다.
- 검색 결과가 없으면 오류가 아닌 `200 OK`와 빈 게시글 목록을 반환한다.

프론트엔드는 빈 검색 결과를 확인해 `검색된 게시글이 없습니다.`라는 안내 문구를
표시한다. 이 문구는 백엔드 오류 메시지가 아닌 화면 표시 정책으로 관리한다.

조회순과 좋아요순은 정렬값과 게시글 ID를 함께 사용하는 복합 커서가 필요하므로 검색
기능 자체에 집중하는 첫 번째 버전에서는 제외하고 이후 고도화 후보로 남긴다.

첫 페이지와 다음 페이지를 조회하는 사이에 게시글이 수정되거나 삭제되면 검색 조건
일치 여부와 결과 순서가 달라질 수 있다. 첫 번째 버전에서는 검색 결과를 특정 시점으로
고정하는 스냅샷 일관성을 보장하지 않는다.

### 1.10. 접근 권한

게시글 검색 기능은 로그인 여부와 관계없이 이용할 수 있다.

- 일반 게시글 목록, 게시글 상세 및 게시글 검색은 공개한다.
- 게시글 작성, 댓글, 좋아요처럼 사용자의 참여가 필요한 기능은 로그인을 요구한다.

처음에는 검색 기능을 회원가입 유도 장치로 사용하기 위해 로그인 사용자에게만
제공하려고 했다. 그러나 이미 공개된 게시글을 검색만 제한해도 보호되는 정보는
늘어나지 않으며, 동일한 `GET /posts` 경로에서 `keyword` 유무에 따라 인증 정책이
달라지는 복잡성이 생긴다. 사용자가 검색을 통해 서비스의 가치를 먼저 경험하고 참여
기능을 이용할 때 로그인을 요구하는 방향이 더 자연스럽다고 판단해 검색을 공개하기로
결정했다.

### 1.11. 잘못된 검색 요청

다음 요청은 `400 Bad Request`로 처리한다.

- 앞뒤 공백 제거 후 검색어가 비어 있는 경우
- 검색어가 2자 미만인 경우
- 검색어가 100자를 초과하는 경우
- `scope`가 `all`, `title`, `content` 중 하나가 아닌 경우
- `keyword` 없이 `scope`만 전달한 경우
- `cursor` 또는 `size`가 기존 페이지네이션 규칙에 맞지 않는 경우

`keyword`와 `scope`를 모두 생략하면 잘못된 검색 요청이 아니라 기존 게시글 목록
조회로 처리한다.

### 1.12. 인수 조건

#### 검색 범위

- `scope=title`이면 제목에 검색어가 포함된 게시글만 반환한다.
- `scope=content`이면 내용에 검색어가 포함된 게시글만 반환한다.
- `scope=all`이면 제목 또는 내용 중 하나에 검색어가 포함된 게시글을 반환한다.
- 제목과 내용이 모두 일치해도 같은 게시글은 한 번만 반환한다.
- `scope`를 생략하면 `all`과 동일하게 동작한다.

#### 검색어 처리

- 검색어의 앞뒤 공백을 제거한 후 검색한다.
- 검색어의 내부 공백은 입력된 형태를 유지한다.
- 공백만 입력한 검색 요청은 거부한다.
- 영문 검색에서는 대소문자를 구분하지 않는다.
- `%`, `_`, `\`는 와일드카드가 아닌 일반 문자로 검색한다.
- 일반 특수문자가 포함된 검색어도 검색할 수 있다.
- 검색어 길이는 앞뒤 공백을 제거한 값을 기준으로 검증한다.

#### 검색 결과

- 삭제된 게시글은 검색 결과에 포함하지 않는다.
- 검색 결과는 최신 게시글 순으로 반환한다.
- 검색 결과가 없으면 빈 목록을 반환한다.
- 커서를 전달하면 해당 커서 이후의 검색 결과를 반환한다.
- 검색 결과가 여러 페이지여도 게시글이 중복되거나 누락되지 않는다.

#### 접근 권한

- 로그인 여부와 관계없이 게시글을 검색할 수 있다.
- 로그인하지 않은 사용자도 일반 목록, 검색 목록 및 게시글 상세를 조회할 수 있다.
- 게시글 작성, 댓글, 좋아요처럼 사용자 참여가 필요한 기능은 기존과 같이 로그인을
  요구한다.

#### 기존 기능 호환성

- `keyword`가 없으면 기존 게시글 목록 조회가 동일하게 동작한다.
- 검색 기능을 추가한 후에도 기존 게시글 목록 테스트가 모두 통과해야 한다.
- 기존 게시글 상세 조회, 작성, 수정, 삭제 기능에 영향을 주지 않아야 한다.

### 1.13. 첫 번째 버전에서 제외할 기능

첫 번째 버전은 DB의 `LIKE '%검색어%'`를 이용한 문자열 포함 검색까지만 구현한다.

- 작성자 검색
- 조회순 및 좋아요순 정렬
- 관련도 기반 정렬
- 오타 교정
- 동의어 및 연관 검색
- 형태소 분석
- 한글 초성 검색
- 검색어 자동완성
- 검색 결과 하이라이트
- 인기 검색어 및 최근 검색어
- Elasticsearch 연동

제외한 기능은 DB 검색 구현과 성능 측정을 완료한 후 필요성과 우선순위를 다시
판단한다.

### 1.14. 1단계에서 배운 점

- 검색 API는 반드시 `/search` 경로를 가져야 하는 것이 아니라, 검색 결과가 기존
  컬렉션과 같은 구조라면 목록 API의 필터로 표현할 수 있다.
- `LIKE '%검색어%'`는 간단한 문자열 포함 검색에는 적합하지만 오타, 동의어, 형태소,
  관련도 같은 검색 기능은 제공하지 않는다.
- 검색어 공백, 길이, 대소문자, 특수문자는 구현 전에 정책을 명확히 정해야 한다.
- 최신순은 기존 게시글 ID 커서를 재사용할 수 있지만 조회순과 좋아요순은 복합 커서와
  변경되는 정렬값의 일관성 문제를 추가로 고려해야 한다.
- 첫 번째 버전의 범위를 제한하면 DB 검색 자체의 동작과 성능에 집중할 수 있다.

## 2. API 설계 이유

### 2.1. 검색 API가 표현하는 자원

게시글 검색 결과는 삭제되지 않은 기존 게시글 목록 중 검색 조건에 일치하는 일부이므로,
별도의 검색 자원으로 보지 않고 게시글 컬렉션에 검색 조건을 적용한 결과로 본다.

검색 결과는 별도의 ID나 생성·수정·삭제 생명주기를 가지지 않으며 기존 게시글 목록과
같은 응답 구조를 사용한다.

### 2.2. API 경로 대안 비교

게시글 검색 API는 기존 게시글 목록에 검색 조건을 추가하는 방식과 검색 전용 경로를
사용하는 방식을 비교했다.

1. `GET /posts?keyword=검색어`
2. `GET /posts/search?keyword=검색어`

첫 번째 방식은 게시글 목록 중 검색 조건과 일치하는 게시글을 조회하는 방법이다.
2.1에서 정의한 기존 게시글 컬렉션의 필터링 결과라는 자원의 의미와 잘 맞고, 기존
`GET /posts` 응답 구조를 재사용할 수 있다. 검색어가 없으면 기존 목록 조회로
자연스럽게 동작하며 별도의 검색 엔드포인트를 추가하지 않아도 된다.

반면 일반 목록과 검색 처리가 하나의 Controller 메서드에 들어갈 수 있고, `keyword`
유무에 따라 Service 로직이 분기될 수 있다. 검색 기능이 복잡해지면 쿼리 파라미터가
늘어날 수 있다.

두 번째 방식은 게시글 검색 기능을 실행해 검색 결과를 조회하는 방법이다. 일반 목록과
검색 요청이 URL로 명확하게 구분되어 Controller와 Service 로직을 분리하기 쉽다.
일반 목록과 검색의 인증 정책을 다르게 적용하기 쉬우며 검색 필터와 정렬 조건이
많아져도 별도 API에서 관리하기 쉽다.

반면 검색 결과가 기존 게시글 목록인데도 별도 경로가 생기며, `/search`는 자원보다
동작을 URL로 표현한 형태에 가깝다. 기존 목록 API와 유사한 응답 및 페이지네이션
처리가 중복될 가능성도 있다.

| 기준 | `GET /posts?keyword=...` | `GET /posts/search?keyword=...` |
| --- | --- | --- |
| 자원의 의미 | 게시글 컬렉션 필터 | 검색 동작을 별도 표현 |
| 2.1 결정과의 일치 | 높음 | 상대적으로 낮음 |
| 기존 응답 재사용 | 자연스러움 | 가능하지만 별도 경로 |
| 일반 목록과 로직 분리 | 분기 필요 | 분리하기 쉬움 |
| 접근 권한 분리 | 복잡할 수 있음 | 쉬움 |
| 검색 기능 확장 | 파라미터 증가 가능 | 별도 관리가 쉬움 |
| 첫 DB 검색의 단순성 | 높음 | 별도 엔드포인트 필요 |

자원의 의미만 보면 `GET /posts`에 검색 조건을 추가하는 방식이 더 자연스럽다고
판단했다. 일반 목록과 검색의 접근 권한 문제를 2.3에서 검토한 뒤 이 경로를 최종
선택했다.

### 2.3. 접근 권한과 API 경로의 충돌 검토

처음에는 비로그인 사용자도 일반 게시글 목록은 조회할 수 있지만 게시글 검색 기능은
로그인 사용자만 이용할 수 있도록 구성하려고 했다. 검색 기능을 회원가입 유도
장치로 활용하려는 목적이었다.

그러나 게시글 목록과 상세 내용이 이미 공개되어 있다면 검색 기능을 제한해도 새로운
정보가 보호되는 것은 아니다. 비로그인 사용자도 게시글 목록을 계속 탐색하면 검색
결과와 동일한 게시글을 찾을 수 있다.

주요 서비스의 접근 정책도 함께 조사했다. 디시인사이드와 당근은 공개 게시글 또는
상품의 검색 결과를 비로그인 사용자에게 제공하고, 댓글 작성이나 거래 채팅처럼
사용자의 참여가 필요한 시점에 로그인을 유도한다. Reddit은 2026년 일부 웹 환경에서
비로그인 접근을 제한하는 실험을 진행했지만 검색만 별도로 회원 전용으로 제한하기보다
웹 탐색과 앱 전환을 포함한 서비스 전반의 접근 정책에 가깝다.

- [Reddit 공식 검색 안내](https://support.reddithelp.com/hc/en-us/articles/19695647891988-How-does-Reddit-search-work)
- [당근 공개 검색 결과](https://www.daangn.com/kr/buy-sell/?search=%EC%95%84%EC%9D%B4%ED%8F%B0)
- [디시인사이드 통합검색](https://search.dcinside.com/)

검색을 공개하면 사용자가 가입하기 전에 원하는 게시글이 존재하는지 확인하고 서비스의
가치를 먼저 경험할 수 있다. 이후 게시글 작성, 댓글, 좋아요처럼 참여가 필요한 기능에서
로그인을 요구하는 편이 더 자연스러운 회원 전환 흐름이라고 판단했다.

검색 요청으로 인한 DB 부하가 우려되더라도 로그인 제한이 직접적인 해결 방법은 아니다.
검색어 최소 길이, 최대 페이지 크기, 요청 횟수 제한과 캐싱 등의 정책으로 별도 대응하는
것이 적절하다.

따라서 접근 정책을 다음과 같이 결정했다.

- `GET /posts`: 비로그인 사용자도 이용할 수 있다.
- `GET /posts/{postId}`: 비로그인 사용자도 이용할 수 있다.
- `GET /posts?keyword=검색어`: 비로그인 사용자도 이용할 수 있다.
- 게시글 작성, 댓글, 좋아요 등 사용자 참여 기능은 로그인이 필요하다.

일반 목록과 검색의 접근 권한이 같아졌으므로 2.2에서 비교한 경로 중 검색 전용
`GET /posts/search`는 사용하지 않고 다음 방식을 최종 선택한다.

```http
GET /posts?keyword=검색어&scope=all
```

### 2.4. 요청 파라미터 정의

예상 요청은 다음과 같다.

```http
GET /posts?keyword=스프링&scope=all&cursor=100&size=10
```

| 파라미터 | 자료형 | 필수 여부 | 기본값 | 의미 |
| --- | --- | --- | --- | --- |
| `keyword` | 문자열 | 선택 | 없음 | 게시글 검색어 |
| `scope` | 문자열 | 선택 | 검색 시 `all` | 검색 대상 필드 |
| `cursor` | 양의 정수 | 선택 | 없음 | 다음 조회를 시작할 기준 게시글 ID |
| `size` | 양의 정수 | 선택 | `10` | 한 번에 반환할 게시글 수 |

`keyword`가 없으면 기존 게시글 목록을 조회하고, 있으면 검색 조건이 적용된 게시글
목록을 조회한다. 빈 문자열과 공백 문자열은 유효한 검색어로 보지 않는다.

`scope`는 `all`, `title`, `content` 중 하나의 소문자 값만 허용한다.

- `keyword`가 있고 `scope`가 없으면 `all`을 적용한다.
- `keyword`와 `scope`가 모두 있으면 선택한 범위에서 검색한다.
- `keyword`가 없고 `scope`만 있으면 잘못된 요청으로 처리한다.
- 허용하지 않은 `scope` 값은 잘못된 요청으로 처리한다.

기존 게시글 목록에서 사용하는 `cursor`와 `size`는 변경하지 않고 검색 결과에도
동일하게 적용한다. `cursor`는 양수여야 하며 `size`는 1 이상 10 이하로 제한한다.

검색 결과의 다음 페이지를 요청할 때는 동일한 `keyword`와 `scope`를 유지하면서 이전
응답의 `next_cursor`를 전달한다. 프론트엔드는 검색어 또는 검색 범위가 변경되면 기존
커서를 제거하고 첫 페이지부터 요청해야 한다.

현재 커서는 게시글 ID만 포함하므로 서버는 해당 커서가 어떤 검색 조건에서 발급됐는지
알 수 없다. 검색 조건과 커서의 관계를 검증하는 불투명 커서는 첫 번째 버전에서
도입하지 않는다.

### 2.5. 검색어 정규화

`keyword`가 없으면 검색어 정규화를 수행하지 않고 기존 게시글 목록을 조회한다.
`keyword`가 전달됐지만 빈 문자열이거나 공백으로만 구성되어 있으면 유효하지 않은
검색 요청으로 처리한다.

검색어 앞뒤의 공백은 Java의 `strip()`을 사용해 제거한다. 첫 번째 버전에서는 검색어
중간의 내부 공백은 입력된 형태로 유지한다.

앞뒤 공백을 제거한 검색어를 기준으로 길이를 검증하며 최소 2자, 최대 100자까지
허용한다.

영문 검색에서는 대소문자를 구분하지 않는다. 검색어는 `Locale.ROOT`를 기준으로
소문자로 변환하고, DB의 제목과 내용에도 `LOWER()`를 적용한 후 비교한다. DB에 저장된
원본 값은 변경하지 않으며 `LOWER()`는 조회 중 비교할 값에만 적용한다.

```text
사용자 검색어: SPRING → spring
DB 저장 제목: Spring Boot
비교할 제목:   LOWER('Spring Boot') → spring boot
검색 패턴:     %spring%
```

검색할 때마다 제목과 내용에 `LOWER()`를 적용하고 검색 패턴도 `%검색어%`처럼 앞부분에
와일드카드를 사용하므로 일반 인덱스를 효율적으로 사용하기 어려울 가능성이 있다. 이로
인한 변환 비용과 검색 성능 저하는 데이터 증가 후 실행 계획과 응답 시간으로 확인한다.

일반 특수문자는 검색어로 허용한다. 다만 `LIKE`에서 특별한 의미를 가지는 `\`, `%`,
`_`는 사용자가 입력한 일반 문자로 검색되도록 escape한다.

정규화와 검증 순서는 다음과 같다.

1. `keyword` 존재 여부를 확인한다.
2. `strip()`으로 앞뒤 공백을 제거한다.
3. 빈 문자열인지 검증한다.
4. 길이가 2자 이상 100자 이하인지 검증한다.
5. `Locale.ROOT`를 기준으로 소문자로 변환한다.
6. `LIKE` 특수문자인 `\`, `%`, `_`를 escape한다.
7. escape한 검색어를 파라미터 바인딩으로 Repository에 전달한다.
8. Repository의 JPQL이 `CONCAT`으로 검색어 앞뒤에 `%`를 추가한다.

`LIKE` escape는 사용자가 입력한 `%`와 `_`가 와일드카드로 동작하지 않게 만들고,
파라미터 바인딩은 검색어를 SQL 또는 JPQL 문자열에 직접 결합하지 않도록 해 SQL
Injection을 방지한다. 검색어 정규화와 escape는 Service가 담당하고, 포함 검색 패턴을
만드는 작업은 Repository 쿼리가 담당한다.

### 2.6. 정상 응답과 오류 응답 정의

검색 결과는 기존 게시글 목록과 같은 자원이므로 기존 응답 구조와 `posts_success`
메시지를 재사용한다.

```json
{
  "message": "posts_success",
  "data": {
    "posts": [],
    "count": 0,
    "has_next": false,
    "next_cursor": null
  }
}
```

`count`는 검색된 전체 게시글 수가 아니라 현재 페이지에 반환한 게시글 수를 의미한다.
전체 결과 수를 구하기 위한 별도의 `COUNT` 쿼리는 첫 번째 버전에서 실행하지 않는다.

검색 결과가 없는 것은 컬렉션 조회의 정상적인 결과이므로 `404 Not Found`가 아닌
`200 OK`와 빈 게시글 목록을 반환한다. 프론트엔드는 빈 배열을 확인해
`검색된 게시글이 없습니다.`라는 안내 문구를 표시한다.

| 상황 | HTTP 상태 | `message` |
| --- | ---: | --- |
| 검색 결과 존재 | 200 | `posts_success` |
| 검색 결과 없음 | 200 | `posts_success` |
| 빈 문자열 또는 공백 검색어 | 400 | `invalid_search_keyword` |
| 검색어 2자 미만 | 400 | `invalid_search_keyword` |
| 검색어 100자 초과 | 400 | `invalid_search_keyword` |
| 잘못된 `scope` | 400 | `invalid_search_scope` |
| `keyword` 없이 `scope`만 전달 | 400 | `invalid_search_keyword` |
| 잘못된 `cursor`, `size` 범위 | 400 | `invalid_pagination_parameter` |
| `cursor`, `size` 타입 오류 | 400 | `invalid_request` |
| 예상하지 못한 서버 오류 | 500 | `internal_server_error` |

검색 기능을 공개하기로 결정했으므로 검색 요청에 별도의 `401 Unauthorized` 응답을
추가하지 않는다.

### 2.7. API 사용 시나리오

정의한 검색 API가 일반 목록 조회, 검색, 페이지네이션과 오류 상황에서 어떻게
동작하는지 요청 시나리오로 확인한다. 이 시나리오는 이후 Controller 테스트 케이스의
기준으로 사용한다.

| 시나리오 | 요청 | 예상 결과 |
| --- | --- | --- |
| 일반 게시글 목록 | `GET /posts` | 기존 게시글 목록을 최신순으로 반환한다. |
| 기본 범위 검색 | `GET /posts?keyword=스프링` | `scope=all`을 적용해 제목 또는 내용에서 검색한다. |
| 제목 검색 | `GET /posts?keyword=스프링&scope=title` | 제목에 검색어가 포함된 게시글만 반환한다. |
| 내용 검색 | `GET /posts?keyword=스프링&scope=content` | 내용에 검색어가 포함된 게시글만 반환한다. |
| 검색 결과 다음 페이지 | `GET /posts?keyword=스프링&scope=all&cursor=73&size=10` | 동일한 조건에서 ID가 73보다 작은 다음 결과를 반환한다. |
| 검색 결과 없음 | `GET /posts?keyword=존재하지않는검색어` | `200 OK`와 빈 게시글 목록을 반환한다. |
| 공백 검색어 | `GET /posts?keyword=%20%20` | `400 Bad Request`와 `invalid_search_keyword`를 반환한다. |
| 너무 짧은 검색어 | `GET /posts?keyword=가` | `400 Bad Request`와 `invalid_search_keyword`를 반환한다. |
| 잘못된 검색 범위 | `GET /posts?keyword=스프링&scope=author` | `400 Bad Request`와 `invalid_search_scope`를 반환한다. |
| 검색어 없는 검색 범위 | `GET /posts?scope=title` | `400 Bad Request`와 `invalid_search_keyword`를 반환한다. |
| 잘못된 페이지 크기 | `GET /posts?keyword=스프링&size=11` | `400 Bad Request`와 `invalid_pagination_parameter`를 반환한다. |
| 비로그인 검색 | `GET /posts?keyword=스프링` | 로그인 여부와 관계없이 동일한 검색 결과를 반환한다. |
| 대소문자 무시 | `GET /posts?keyword=SPRING` | 영문 대소문자와 관계없이 일치하는 게시글을 반환한다. |
| 일반 특수문자 검색 | `GET /posts?keyword=C%2B%2B` | `C++`가 포함된 게시글을 반환한다. |

검색 결과의 다음 페이지를 조회할 때는 처음 요청과 동일한 `keyword`와 `scope`를
전달한다. 검색어 또는 검색 범위가 변경되면 프론트엔드는 기존 커서를 제거하고 첫
페이지부터 다시 요청한다.

## 3. DB 검색 쿼리 선택

### 3.1. 쿼리 구현 방식 분석

현재 프로젝트는 H2를 사용하지만 이후 다른 관계형 데이터베이스로 변경될 가능성이
있다. 기존 게시글 목록 조회가 JPQL로 구현되어 있으며 검색 기능에서도 삭제 여부,
검색 범위, 커서 및 정렬 조건을 명시적으로 표현해야 한다.

기존 코드와의 일관성, 유지보수성 및 데이터베이스 변경 가능성을 고려해 검색 쿼리도
JPQL `@Query` 방식으로 구현하기로 결정했다.

다만 JPQL이 완전한 데이터베이스 독립성을 보장하는 것은 아니다. 대소문자 비교,
문자열 정렬, `LIKE` 처리 및 인덱스 사용 방식은 데이터베이스에 따라 달라질 수 있다.
JPQL은 애플리케이션 시작 시점이나 쿼리 실행 시점에 오류가 발견될 수 있으므로
Repository 테스트와 실제 실행 SQL 확인이 필요하다.

검색 조건이 계속 증가하면 하나의 JPQL에 많은 분기 조건이 들어가거나 비슷한 쿼리가
반복될 수 있다. 현재 검색 범위는 `all`, `title`, `content`로 고정되어 있으므로
QueryDSL을 바로 도입하지 않고, 선택 조건이 실제로 복잡해지는 시점에 동적 쿼리
도입을 다시 검토한다.

QueryDSL은 실행할 조건을 Java 코드로 조립할 수 있는 동적 쿼리 도구이지만,
`LIKE '%검색어%'` 자체의 성능 문제를 해결하는 검색 엔진은 아니다.

### 3.2. 검색 조건과 책임 경계 설계

처음에는 Controller가 `keyword` 유무를 판단한 뒤 일반 게시글 조회 또는 검색 게시글
조회에 적절한 Service 메서드를 호출하는 구조를 생각했다. 하지만 이 구조에서는
Controller가 검색어 존재 여부뿐 아니라 공백 처리와 유효성 검사 같은 검색 규칙까지
알게 될 가능성이 있었다.

따라서 Controller는 `keyword`, `scope`, `cursor`, `size` 등의 요청 파라미터를
가공하지 않고 Service에 전달하도록 책임을 정했다.

Service는 다음 검색 규칙을 담당한다.

- `keyword`가 전달되지 않으면 기존 게시글 목록 조회를 선택한다.
- `keyword`가 전달되면 앞뒤 공백 제거, 길이 및 검색 범위를 검증한다.
- 검색어를 `Locale.ROOT` 기준 소문자로 변환한다.
- `LIKE`에서 특별한 의미를 가지는 `\`, `%`, `_`를 일반 문자로 검색하도록
  escape한다.
- `scope`에 맞는 Repository 검색 메서드를 선택한다.
- Repository 결과를 기존 커서 페이지 응답으로 변환한다.

`keyword`가 전달됐지만 앞뒤 공백을 제거한 결과가 비어 있으면 일반 목록으로
처리하지 않고 잘못된 검색 요청으로 처리한다. 검색어가 없는 요청과 잘못된 검색어를
구분하는 것은 검색 기능의 비즈니스 규칙이므로 Service에서 일관되게 관리한다.

Repository는 Service에서 전달받은 검색 조건으로 JPQL을 실행하는 역할을 담당한다.
검색 범위가 세 가지로 고정되어 있으므로 하나의 쿼리 안에서 `scope`를 분기하지 않고
다음 세 메서드로 분리했다.

- `searchPostsByTitle`
- `searchPostsByContent`
- `searchPostsByTitleOrContent`

세 쿼리에는 다음 공통 조건이 반복된다.

```jpql
JOIN FETCH p.author
WHERE p.deletedAt IS NULL
AND (:cursor IS NULL OR p.id < :cursor)
ORDER BY p.id DESC
```

`JOIN FETCH p.author`는 게시글 목록 응답에서 작성자 정보를 사용할 때 게시글마다
작성자를 추가 조회하는 N+1 문제를 방지하기 위해 기존 목록 쿼리와 동일하게
유지했다. `Post`와 `author`는 다대일 관계이므로 컬렉션 fetch join에서 발생할 수 있는
페이지네이션 문제와는 성격이 다르다.

첫 페이지에서는 `cursor`가 `null`이므로 모든 검색 결과를 대상으로 한다. 다음
페이지에서는 마지막으로 조회한 게시글 ID를 커서로 전달하고, 최신 게시글일수록 ID가
크다는 현재 모델을 기준으로 `p.id < :cursor`인 게시글을 조회한다.

포함 검색의 앞뒤 `%`는 Repository의 `CONCAT`이 추가한다. Service가 검색어를
정규화하고 escape하는 책임과 Repository가 실제 검색 패턴을 구성하고 조회하는 책임을
구분했다.

### 3.3. Repository 테스트와 실행 쿼리 확인

작성한 JPQL이 요구사항대로 동작하는지 확인하기 위해 `@DataJpaTest`로 Repository
테스트를 작성했다.

테스트를 통해 다음 동작을 확인했다.

- 제목에 검색어가 포함된 게시글 조회
- 내용에 검색어가 포함된 게시글 조회
- 제목 또는 내용에 검색어가 포함된 게시글 조회
- 영문 대소문자를 구분하지 않는 내용 검색
- 검색어가 포함되어도 삭제된 게시글은 제외
- 커서 게시글 자체와 커서보다 최신인 게시글은 제외
- 게시글 ID 내림차순 정렬
- `Pageable`을 이용한 조회 개수 제한

전체 검색에서는 제목과 내용의 검색 조건을 괄호로 묶었다.

```jpql
AND (
    LOWER(p.title) LIKE CONCAT('%', :keyword, '%') ESCAPE '\\'
    OR LOWER(p.content) LIKE CONCAT('%', :keyword, '%') ESCAPE '\\'
)
```

괄호가 없으면 `AND`가 `OR`보다 먼저 계산되는 연산자 우선순위 때문에 내용에
검색어가 포함된 삭제 게시글이 결과에 포함될 수 있다. 이 오류를 잡을 수 있도록
검색어가 내용에만 포함된 삭제 게시글을 만들고 검색 결과에서 제외되는지 검증했다.

커서 테스트에서는 게시글 네 개를 저장한 뒤 가장 최신 게시글 ID를 커서로 전달했다.
그 결과 커서보다 ID가 작은 게시글 중 최신 두 개가 ID 내림차순으로 반환되는지
확인했다. 이를 통해 커서 조건, 정렬 및 조회 개수 제한을 하나의 시나리오로 검증했다.

#### CLOB과 `LOWER()` 호환 문제

내용 검색 쿼리를 처음 실행했을 때 `Post.content`가 `@Lob`으로 선언되어 H2의
`CLOB`으로 매핑됐고, Hibernate가 `LOWER(p.content)`의 인자로 CLOB을 허용하지 않아
Repository 초기화 과정에서 오류가 발생했다.

문자열로 형변환하는 방법과 Hibernate의 `ILIKE`를 사용하는 방법도 검토했다. 그러나
검색할 때마다 형변환이 발생할 수 있고 데이터베이스별 변환 및 길이 처리 차이가
생길 수 있었다. `ILIKE`도 모든 관계형 데이터베이스에서 동일하게 사용할 수 있는
JPQL 표준 기능이 아니다.

Discourse와 Stack Exchange 등 실제 커뮤니티 서비스의 게시글 길이 제한을 참고해
게시글 내용의 최대 길이를 32,000자로 결정했다. 이에 따라 엔티티의 `@Lob`을 제거하고
다음과 같이 변경했다.

```java
@Column(nullable = false, length = 32_000)
private String content;
```

게시글 생성 및 수정 요청 DTO에도 `@Size(max = 32_000)`를 추가했다. `@Size`는 API
요청 단계에서 잘못된 길이를 검증하고, `@Column(length = 32_000)`은 데이터베이스
스키마의 최대 길이를 표현한다.

H2 테스트 스키마에서 `content`가 `VARCHAR(32000)`으로 생성되는 것을 확인했다. 실제
파일 기반 H2 데이터베이스도 변경 전에 백업한 뒤 애플리케이션을 실행해 CLOB에서
`VARCHAR(32000)`으로 변경되는 SQL을 확인했다. 변경 후 기존 게시글 20개가 유지되고
가장 긴 기존 본문도 새 제한 안에 있는 것을 확인했다.

변경 후 Hibernate가 H2에서 실행한 내용 검색 조건은 다음 형태였다.

```sql
lower(p.content) like ('%' || ? || '%') escape '\'
```

JPQL의 `CONCAT`은 H2에서 문자열 연결 연산자로 변환됐고, 검색어는 SQL 문자열에 직접
삽입되지 않고 바인딩 파라미터 `?`로 전달됐다. 삭제 조건, 커서 조건, ID 내림차순 및
조회 개수 제한도 생성된 SQL에 포함되는 것을 확인했다.

추가한 검색 테스트를 포함한 `PostRepositoryTest` 전체를 실행해 기존 Repository
기능과 검색 쿼리가 함께 통과하는 것을 확인했다.

이번 단계에서는 `ESCAPE '\\'` 문법이 쿼리에 포함되는 것까지만 확인했다. 사용자가
입력한 `%`, `_`, `\`를 Service에서 실제로 escape하는 로직과 그 결과는 4단계의
Service 구현 및 테스트에서 검증한다.

### 3.4. 최종 선택과 검토

첫 번째 DB 검색 버전에서는 JPQL `@Query`와 검색 범위별 Repository 메서드 세 개를
사용하기로 최종 결정했다.

| 결정 항목 | 선택 |
| --- | --- |
| 쿼리 방식 | JPQL `@Query` |
| 검색 범위 처리 | 제목, 내용, 전체 검색 메서드 분리 |
| 삭제 조건 | `p.deletedAt IS NULL` |
| 커서 조건 | 첫 페이지는 `null`, 다음 페이지는 `p.id < :cursor` |
| 정렬 | `p.id DESC` |
| 작성자 조회 | `JOIN FETCH p.author` |
| 포함 검색 | Repository에서 `CONCAT('%', :keyword, '%')` |
| 대소문자 비교 | DB 필드에 `LOWER()`, Service에서 검색어 소문자 변환 |
| LIKE 특수문자 | JPQL의 `ESCAPE '\\'`와 Service의 검색어 escape 조합 |
| 본문 저장 타입 | 최대 32,000자의 문자열 컬럼 |
| 동적 쿼리 | 현재는 도입하지 않고 검색 조건 증가 시 QueryDSL 재검토 |

#### 3단계 완료 체크포인트

- [x] 기존 코드와 확장 가능성을 근거로 JPQL `@Query`를 선택했다.
- [x] Controller, Service 및 Repository의 검색 책임 경계를 구분했다.
- [x] 제목, 내용 및 전체 검색 Repository 메서드를 구현했다.
- [x] 삭제 조건, 커서 조건, ID 내림차순, 조회 개수 제한 및 작성자 fetch join을
  쿼리에 반영했다.
- [x] CLOB과 `LOWER()`의 호환 문제를 확인하고 본문 길이 정책과 문자열 컬럼 매핑으로
  해결했다.
- [x] 정상 검색, 대소문자, OR 조건, 삭제 제외, 커서, 정렬 및 조회 개수 제한을
  Repository 테스트로 검증했다.
- [x] Hibernate가 생성한 SQL에서 join, 삭제 조건, 커서, `LOWER()`와 `LIKE`,
  `ESCAPE`, ID 내림차순 및 행 개수 제한을 확인했다.
- [x] 현재 방식의 중복과 DB별 차이, `LIKE '%검색어%'`의 성능 한계를 기록하고
  QueryDSL 및 Elasticsearch 재검토 시점을 구분했다.

전체 백엔드 테스트 81개를 다시 실행한 결과 실패와 오류 없이 모두 통과했다.

사용자 입력의 `%`, `_`, `\`를 실제로 escape하는 동작은 Service가 구현되어야 검증할
수 있으므로 3단계의 미완료 항목이 아니라 4단계의 완료 조건으로 유지한다.

세 JPQL에 삭제, 커서, 정렬 및 fetch join 조건이 반복되는 단점은 있다. 그러나 현재는
검색 범위가 세 가지로 명확하게 고정되어 있어 각 쿼리의 목적과 실행 조건을 직접
읽고 테스트하기 쉽다는 장점이 더 크다고 판단했다.

`LOWER()`와 앞부분 와일드카드가 포함된 `LIKE '%검색어%'`는 일반 인덱스를 효율적으로
사용하기 어렵고, 게시글 수가 늘면 전체 스캔과 문자열 비교 비용이 증가할 가능성이
있다. 이 문제를 지금 미리 다른 기술로 감추지 않고 6~8단계에서 실행 계획과 응답
시간을 측정해 DB 검색의 기준선과 한계를 직접 확인한다.

3단계를 통해 JPQL 문법만 올바르게 작성하는 것으로는 충분하지 않고, 엔티티 필드가
실제 데이터베이스에서 어떤 자료형으로 매핑되는지와 DB가 생성된 SQL을 어떻게
실행하는지까지 확인해야 한다는 점을 배웠다. 또한 테스트는 정상 검색 결과뿐 아니라
연산자 우선순위, 삭제 조건, 커서 방향 및 페이지 크기 같은 경계 조건을 검증하는
설계 도구라는 점을 확인했다.

## 5. 백엔드 테스트

백엔드 검색 기능을 Service 단위 테스트, Controller 슬라이스 테스트 및 통합 테스트로
나누어 검증했다. 각 테스트가 같은 동작을 반복해서 확인하기보다 해당 계층이 담당하는
책임과 계층 사이의 연결을 확인하도록 범위를 구분했다.

### 5.1. PostService 단위 테스트

검색어 정규화와 검증, 검색 범위에 따른 Repository 메서드 선택 및 커서 페이지 응답
생성은 Service의 책임이다. 따라서 실제 `PostService`를 사용하고 Repository는 Mockito
Mock 객체로 대체해 DB 동작과 분리된 상태에서 검색 규칙을 검증했다.

`ArgumentCaptor`를 사용해 Service가 Repository에 전달한 값을 확인했다. 이를 통해
검색어의 앞뒤 공백이 제거되는지, 내부 공백은 유지되는지, 영문은 소문자로 변환되는지,
`\`, `%`, `_`가 올바른 순서로 escape되는지를 검증했다. Repository의 반환 결과만
확인했다면 Service가 잘못된 검색어를 전달해도 테스트가 통과할 수 있으므로, 계층
경계에서 실제 전달값을 확인했다.

검색 범위는 다음과 같이 검증했다.

- `scope`가 없거나 `all`이면 제목 또는 내용 검색 메서드를 호출한다.
- `title`이면 제목 검색 메서드를 호출한다.
- `content`이면 내용 검색 메서드를 호출한다.
- 허용하지 않은 검색 범위는 Repository를 호출하지 않고
  `InvalidSearchScopeException`을 발생시킨다.
- `keyword` 없이 `scope`만 전달하면 `InvalidSearchKeywordException`을 발생시킨다.

빈 문자열, 공백 문자열, 2자 미만 및 100자 초과 검색어를 매개변수화 테스트로
검증했다. 잘못된 검색어와 잘못된 `cursor`, `size`는 Repository를 호출하기 전에
예외가 발생하는지도 확인했다. 같은 검증 구조를 여러 테스트에서 반복하지 않고
입력값과 예상 결과만 바꿔 경계값을 읽기 쉽게 구성했다.

완료 체크포인트를 역검증하는 과정에서 허용 범위 바로 바깥의 1자와 101자는
검증했지만, 정확한 허용 경계인 2자와 100자는 명시적으로 검증하지 않았다는 점을
발견했다. 두 경계값이 실제 검색 쿼리 호출까지 도달하는 매개변수화 테스트를 추가해
`min-1`, `min`, `max`, `max+1` 조건을 모두 확인했다.

커서 응답은 요청한 크기보다 한 건 더 조회하는 look-ahead 방식을 기준으로 검증했다.
요청 크기가 2일 때 세 건이 조회되면 실제 응답에는 최신 두 건만 포함하고
`has_next=true`와 실제 마지막 반환 게시글 ID를 `next_cursor`로 설정하는지 확인했다.
정확히 두 건만 조회되면 `has_next=false`, `next_cursor=null`이 되는 것도 검증했다.
추가 조회한 게시글의 ID를 커서로 반환하면 다음 페이지에서 해당 게시글이 누락되므로,
커서는 반드시 클라이언트에 실제로 반환한 마지막 게시글을 기준으로 해야 한다.

private 메서드를 직접 테스트하지 않고 공개 메서드인 `getPosts()`의 입력과 출력 및
협력 객체 호출을 통해 정규화와 escape 동작을 확인했다. 이를 통해 테스트가 내부 구현
형태보다 Service가 외부에 제공하는 동작에 집중하도록 구성했다.

검색 테스트를 포함한 `PostServiceTest`의 33개 테스트가 모두 통과했다.

### 5.2. Controller 슬라이스 테스트

게시글 검색 요청의 쿼리 파라미터가 요청 DTO에 정상적으로 바인딩되고, Service의 처리
결과가 약속한 HTTP 응답으로 변환되는지 확인했다.

`@WebMvcTest`를 사용해 전체 애플리케이션을 실행하지 않고 Controller, 요청 바인딩,
전역 예외 처리 및 JSON 응답과 같은 웹 계층만 분리해 검증했다. 검색 규칙 자체는
5.1의 Service 단위 테스트에서 확인했으므로 Service는 Mock 객체로 대체하고, 이번
단계에서는 Controller와 HTTP 계약에 집중했다.

검색 파라미터가 없으면 `keyword`, `scope`, `cursor`는 `null`이고 `size`에는 기본값
10이 적용되는지 확인했다. 모든 검색 파라미터를 전달한 경우에는 Controller가
정규화하거나 판단하지 않고 입력값을 그대로 `PostListRequest`에 바인딩해 Service로
전달하는지도 검증했다.

`cursor=abc` 또는 `size=abc`처럼 요청 문자열을 DTO의 자료형으로 변환할 수 없는
경우에는 Service가 호출되기 전에 Spring의 데이터 바인딩 단계에서 요청이 거부되고
`400 Bad Request`와 `invalid_request`가 반환되는 것을 확인했다. 이를 통해 Java 코드의
컴파일 성공과 실제 HTTP 요청값의 런타임 변환 성공은 별개의 문제라는 점을 확인했다.

Service에서 `InvalidSearchKeywordException` 또는 `InvalidSearchScopeException`이
발생한 상황을 Mock으로 만들고, 전역 예외 처리기가 각각
`invalid_search_keyword`, `invalid_search_scope`를 포함한 400 응답으로 변환하는지
검증했다. 비로그인 요청도 보안 필터를 통과해 게시글 목록과 검색 기능을 이용할 수
있는지 함께 확인했다.

Controller 슬라이스 테스트는 검색 기능 자체를 다시 검사하는 테스트가 아니라 HTTP
요청과 애플리케이션 내부 로직 사이의 연결을 검사하는 테스트라는 점을 학습했다.
`PostControllerTest`의 10개 테스트가 모두 통과했다.

### 5.3. 통합·회귀 테스트

단위 테스트와 Controller 슬라이스 테스트를 통해 각 계층의 동작을 개별적으로
검증했지만, 실제 계층들이 연결된 상태에서도 검색 기능이 정상적으로 동작하는지
확인할 필요가 있었다.

`@SpringBootTest`와 `MockMvc`를 사용해 실제 Controller, Service, Repository 및 H2
데이터베이스를 연결했다. 실제 서버 포트를 열지는 않지만 애플리케이션의 Bean과
Spring MVC 요청 흐름을 사용해 다음 대표 시나리오를 검증했다.

- 비로그인 사용자의 전체 검색
- 제목 또는 내용 일치와 영문 대소문자 무시
- 삭제된 게시글 제외와 작성자 정보 응답
- `%`, `_`, `\`를 와일드카드가 아닌 입력된 문자 그대로 검색
- 첫 응답의 `next_cursor`를 사용한 다음 페이지 조회
- 검색 결과가 없을 때 200과 빈 커서 페이지 응답
- 잘못된 검색어와 검색 범위의 실제 400 응답

특히 `%`, `_`, `\` 검색은 Service 단위 테스트에서 escape된 문자열이 Repository로
전달되는 것까지만 확인할 수 있다. 실제 JPQL의 `ESCAPE`와 H2의 `LIKE`가 결합된
상태에서도 의도대로 일치하는지는 Mock Repository로 보장할 수 없으므로 통합
테스트에서 확인했다.

커서 페이지네이션은 첫 번째 검색 응답의 `next_cursor`를 두 번째 요청에 직접
전달했다. 첫 페이지와 다음 페이지 사이에 게시글이 중복되거나 누락되지 않고
ID 내림차순으로 반환되는지 실제 API 사용 흐름으로 검증했다.

각 통합 테스트에는 `@Transactional`을 적용했다. 테스트가 저장한 사용자와 게시글은
테스트 종료 후 롤백되므로 테스트 실행 순서와 관계없이 서로 독립된 데이터를
사용한다. 추가한 `PostSearchIntegrationTest`의 5개 테스트가 모두 통과했다.

통합 테스트가 통과한 후 전체 테스트를 다시 실행해 검색 기능 추가가 기존 회원,
게시글, 파일 저장, 보안 및 예외 처리 기능에 영향을 주지 않았는지 회귀 검증했다.
전체 백엔드 테스트 111개가 실패와 오류 없이 모두 통과했다.

#### 5단계 완료 체크포인트

- [x] 검색어 정규화, 길이 검증 및 LIKE 특수문자 escape를 Service 단위 테스트로
  검증했다.
- [x] 검색어 길이의 `min-1`, `min`, `max`, `max+1` 경계값을 모두 검증했다.
- [x] 검색 범위에 따라 올바른 Repository 메서드를 선택하고 다른 검색 메서드를
  호출하지 않는지 확인했다.
- [x] 잘못된 검색어, 검색 범위 및 페이지 파라미터에서는 Repository를 호출하기 전에
  오류가 발생하는지 확인했다.
- [x] size보다 한 건 더 조회하는 방식으로 `count`, `has_next`, `next_cursor`가
  생성되는 경계 조건을 검증했다.
- [x] 검색 쿼리 파라미터의 DTO 바인딩과 기본값 적용을 Controller 테스트로
  확인했다.
- [x] 자료형 변환 오류와 검색 예외가 정의한 400 응답으로 변환되는지 확인했다.
- [x] 비로그인 사용자도 검색 요청을 이용할 수 있는지 확인했다.
- [x] 실제 Controller, Service, Repository 및 H2가 연결된 상태에서 대표 검색
  시나리오를 검증했다.
- [x] 실제 H2에서 `%`, `_`, `\`가 일반 문자로 검색되는지 확인했다.
- [x] 검색 결과가 없으면 200과 빈 목록 및 빈 커서 정보를 반환하는지 확인했다.
- [x] 첫 응답의 커서를 다음 요청에 사용해 페이지 사이에 중복이나 누락이 없는지
  확인했다.
- [x] 전체 회귀 테스트 111개가 실패와 오류 없이 통과했다.

이번 단계를 통해 모든 테스트에서 실제 객체를 사용하는 것이 항상 더 좋은 것은
아니며, 검증하려는 책임에 따라 테스트 범위와 대역을 선택해야 한다는 점을 배웠다.
Service 단위 테스트는 비즈니스 규칙, Controller 슬라이스 테스트는 HTTP 요청과 응답,
통합 테스트는 계층의 실제 연결을 검증한다. 회귀 테스트는 별도의 테스트 종류가
아니라 새 변경이 기존 동작을 깨뜨리지 않았는지 기존 테스트 전체를 다시 실행해
확인하는 과정이라는 점도 구분하게 됐다.

## 6. 성능 실험 설계와 H2 기준선 측정

### 6.1. 실험 목적과 판단 기준

DB의 `LOWER(column) LIKE '%keyword%'` 방식이 게시글 증가에 따라 어떻게 변하는지
확인하기 위해 게시글을 1천 건, 1만 건, 10만 건으로 늘리며 측정했다. 원래 50만
건까지 측정할 계획이었지만, 10만 건에서 단일 사용자 응답 시간과 목표 부하 처리량이
서비스에 적용하기 어려운 수준에 도달해 50만 건 측정은 진행하지 않았다.

이번 단계에서는 두 종류의 도구를 구분해 사용했다.

- H2 `EXPLAIN ANALYZE`: DB가 어떤 테이블과 인덱스를 사용하고 몇 개의 행을
  확인했는지 분석한다.
- k6: 실제 HTTP 요청을 통해 애플리케이션 전체의 응답 시간, 처리량, 오류 및 요청
  누락을 측정한다.

H2는 개발 및 기준선 측정 환경이므로 이 결과를 PostgreSQL의 실행 계획으로 일반화하지
않는다. 이번 측정의 목적은 현재 구현의 데이터 증가 추세와 실패 지점을 확인하고,
후속 PostgreSQL 측정과 비교할 기준선을 만드는 것이다.

### 6.2. 재현 가능한 벤치마크 데이터 설계

데이터 규모가 달라도 같은 조건을 재현할 수 있도록 벤치마크 전용 Spring 프로필과
대량 데이터 생성기를 구성했다.

| 항목 | 설정 |
| --- | --- |
| 게시글 수 | 1,000 / 10,000 / 100,000건 |
| 작성자 수 | 100명 |
| 난수 seed | `20260802` |
| 삭제 게시글 | 전체의 5%, 매 20번째 게시글 |
| 활성 게시글 | 전체의 95% |

제목 길이는 20~80자로 만들고, 본문은 실제로 길이가 다양한 게시글이 섞이는 상황을
재현하도록 다음 비율로 생성했다.

| 본문 길이 | 분포 |
| --- | ---: |
| 300~799자 | 60% |
| 800~1,999자 | 30% |
| 2,000~7,999자 | 9% |
| 16,000~32,000자 | 1% |

대량 생성은 JPA 객체를 한꺼번에 메모리에 보관하지 않고 설정한 크기만큼 JDBC batch로
나눠 저장했다. 운영 데이터에 실수로 데이터를 생성하지 않도록 `benchmark` 프로필과
`benchmark-data` 경로에서만 생성기를 실행하며, 대상 DB에 기존 사용자나 게시글이
있으면 생성을 중단한다. 생성 완료 후에는 설정한 작성자 수와 게시글 수가 실제 저장
건수와 같은지도 다시 검증했다.

검색어는 실제 일치 건수와 위치를 통제할 수 있도록 일반 문장에 우연히 등장하기 어려운
고정 문자열을 사용했다. 검색어 표식은 삭제되지 않은 게시글 순서를 기준으로 전체
범위에 고르게 분산했다.

| 검색어 | 목적 | 활성 게시글 내 분포 | 1천 건 | 1만 건 | 10만 건 |
| --- | --- | ---: | ---: | ---: | ---: |
| `qzcommona91x` | common | 10개마다 1개 | 95 | 950 | 9,500 |
| `rxmediumb82y` | medium | 100개마다 1개 | 9 | 95 | 950 |
| `tvrarec73z` | rare | 1,000개마다 1개 | 0 | 9 | 95 |
| `wxfixedd64k` | fixed | 전체 범위에 정확히 10개 | 10 | 10 | 10 |
| `ypscopee55m` | 범위 비교 | 100개마다 제목과 내용 모두 삽입 | 9 | 95 | 950 |
| `zvneverf46n` | 불일치 비교 | 삽입하지 않음 | 0 | 0 | 0 |

동일한 seed와 설정을 사용하면 데이터의 문자열과 검색어 분포가 재현된다. 이를 통해
실행할 때마다 우연히 다른 데이터가 생성되어 결과 비교가 흔들리는 문제를 줄였다.

### 6.3. H2 측정 방법

대표 쿼리는 검색 결과 10건과 다음 페이지 존재 여부를 확인하기 위해 최대 11건을
조회한다.

```sql
EXPLAIN ANALYZE
SELECT p.*, u.*
FROM posts p
JOIN users u ON u.user_id = p.user_id
WHERE p.deleted_at IS NULL
  AND (
       LOWER(p.title) LIKE '%qzcommona91x%' ESCAPE '\'
       OR LOWER(p.content) LIKE '%qzcommona91x%' ESCAPE '\'
  )
ORDER BY p.post_id DESC
FETCH FIRST 11 ROWS ONLY;
```

첫 실행은 H2, JVM 및 운영체제 파일 캐시의 워밍업 영향을 크게 받을 수 있어 단발
실행시간으로 판단하지 않았다. 조건별로 워밍업한 뒤 실행 순서를 교차하고, 1천 건은
5회, 1만 건과 10만 건은 3회 반복해 중앙값을 대표값으로 사용했다.

`scanCount`는 애플리케이션에 반환된 행의 수가 아니라 실행 과정에서 해당 테이블 또는
인덱스를 통해 확인한 행의 수를 뜻한다. 현재 계획의 `POSTS scanCount`는 `POSTS`
테이블을 문자 그대로 한 번 순차 스캔했다는 의미라기보다, 작성자별 `USER_ID` 외래 키
인덱스 탐색 과정에서 누적해 확인한 게시글 수다.

### 6.4. H2 실행 계획 측정 결과

#### 6.4.1. 데이터 규모 비교

검색어 `qzcommona91x`, 검색 범위 `all`, 커서 없음 조건의 대표값이다.

| 데이터 수 | USERS scanCount | POSTS scanCount | 실행시간 중앙값 |
| ---: | ---: | ---: | ---: |
| 1,000 | 101 | 1,100 | 13ms |
| 10,000 | 101 | 10,100 | 150ms |
| 100,000 | 101 | 100,100 | 2,929ms |

세 규모 모두 H2가 `USERS`를 먼저 확인하고 `USER_ID` 외래 키 인덱스로 각 작성자의
게시글을 조인하는 유사한 계획을 선택했다. 최대 11건만 반환하지만 검색 조건을 평가하고
최신순으로 정렬하기 위해 전체 게시글에 가까운 범위를 확인했다. 게시글이 10배씩
증가하면서 `POSTS scanCount`도 거의 10배씩 증가했고 실행시간도 함께 늘었다.

테이블에는 저장 순서라는 의미가 없으므로 `ORDER BY p.post_id DESC`와 `LIMIT`만으로
DB가 항상 최신 게시글부터 검색해 11건을 찾는 즉시 중단하는 것은 아니다. 옵티마이저가
기본 키의 정렬 순서를 활용하는 계획을 선택해야 조기 종료가 가능하지만, 현재 기본
검색 계획은 작성자를 먼저 조인한 뒤 검색 조건을 평가하고 정렬했다.

#### 6.4.2. 검색어 빈도 비교

| 데이터 수 | common | fixed | none | rare |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 13ms | 12ms | 13ms | - |
| 10,000 | 150ms | 136ms | 146ms | 170ms |
| 100,000 | 2,929ms | 2,731ms | 2,691ms | 4,071ms |

검색어의 일치 건수는 크게 달랐지만 같은 데이터 규모에서는 실행 계획과 `scanCount`가
동일했다. 현재 계획에서는 결과가 흔한지 희소한지보다 전체 게시글에 가까운 범위를
확인하는 비용이 더 크게 작용했다. rare 검색의 시간이 더 길게 측정됐지만 반복 수와
실행 환경의 변동을 고려하면 희소 검색이 구조적으로 항상 더 느리다고 단정하지 않았다.

#### 6.4.3. 검색 범위 비교

같은 게시글의 제목과 내용에 모두 포함된 `ypscopee55m`을 사용해 일치 결과의 위치를
고정하고 검색 범위만 변경했다.

| 데이터 수 | title | content | all |
| ---: | ---: | ---: | ---: |
| 1,000 | 4ms | 20ms | 19ms |
| 10,000 | 37ms | 147ms | 194ms |
| 100,000 | 1,813ms | 2,642ms | 2,703ms |

세 범위의 `scanCount`는 같았지만 제목 검색이 더 빨랐다. 본문은 제목보다 문자열이
길어 각 행에서 `LOWER()` 변환과 `LIKE` 비교에 더 많은 CPU 작업이 필요하다. `all`은
제목과 내용의 OR 조건까지 평가하므로 가장 많은 문자열 연산이 필요할 수 있다. 따라서
`scanCount`가 같아도 행마다 수행되는 함수와 문자열 비교 비용에 따라 실행시간은 달라질
수 있다.

#### 6.4.4. 커서 위치 비교

검색어는 `qzcommona91x`, 범위는 `all`로 고정하고 커서를 전체 ID 범위의 75%, 50%,
25% 위치로 이동했다.

| 데이터 수 | 커서 없음 | 75% | 50% | 25% | POSTS scanCount |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 16ms | 10ms | 10ms | 8ms | 1,100 |
| 10,000 | 150ms | 117ms | 161ms | 67ms | 10,100 |
| 100,000 | 2,929ms | 2,459ms | 2,203ms | 1,958ms | 100,100 |

실제 Repository 쿼리와 같은 nullable 커서 조건은 다음 형태다.

```sql
AND (@cursor IS NULL OR p.post_id < @cursor)
```

커서가 작아져 검색 가능한 ID 범위가 줄어도 실행 계획과 `scanCount`는 감소하지 않았다.
H2는 이 OR 조건을 기본 키 범위 탐색의 시작 조건으로 사용하지 않고, 게시글을 조인한
후 적용하는 필터로 처리했다. 실행시간이 일부 줄어든 이유는 커서에서 제외된 행에 대해
제목과 본문의 문자열 비교를 건너뛸 수 있기 때문으로 판단했다.

#### 6.4.5. 고정 커서 조건 진단

nullable OR가 계획에 미치는 영향을 분리해 확인하기 위해 10만 건 데이터에서 커서를
상수 범위 조건으로 바꿨다.

```sql
AND p.post_id < 50000
```

| 조건 | 시작 테이블과 인덱스 | POSTS scanCount | USERS scanCount | 실행시간 중앙값 |
| --- | --- | ---: | ---: | ---: |
| `@cursor IS NULL OR p.post_id < @cursor` | USERS → USER_ID FK | 100,100 | 101 | 2,203ms |
| `p.post_id < 50000` | POSTS → POST_ID PK 범위 | 107 | 21 | 6ms |

상수 조건에서는 H2가 `POSTS` 기본 키 범위를 내림차순으로 탐색하고 `index sorted`로
정렬 순서를 활용했다. common 검색어는 10개마다 존재하므로 11건을 찾은 뒤 빠르게
중단할 수 있었다. 이 진단은 쿼리 형태가 실행 계획에 큰 영향을 줄 수 있음을 보여준다.
다만 결과가 매우 희소하거나 없는 검색어는 상수 커서 조건에서도 더 넓은 범위를 확인할
수 있으므로 모든 검색이 6ms가 된다는 의미는 아니다. 이 결과는 공식 기준선이 아니라
nullable OR 조건 개선 가능성을 확인한 보조 실험으로 사용한다.

### 6.5. k6 HTTP 부하 테스트

#### 6.5.1. 테스트 구성

모든 요청은 `qzcommona91x`, `scope=all`, `size=10` 조건을 사용했다. k6는 다음 계약을
매 요청마다 검사했다.

- HTTP 상태가 200이다.
- 응답이 JSON이다.
- 게시글이 10건 반환된다.
- 다음 페이지가 존재한다.

본 측정 전에 스모크 테스트로 스크립트와 API 계약을 확인하고 워밍업을 실행했다.
스모크 테스트와 워밍업 결과는 공식 성능 결과에 포함하지 않았다.

1 VU 테스트는 한 사용자가 응답을 받은 뒤 다음 요청을 보내는 closed-loop 방식으로
60초간 실행했다. 이 처리량은 서버의 최대 처리량이 아니라 단일 사용자가 연속 요청할
때 달성한 처리량이다.

공식 부하 테스트는 1초마다 50개의 요청을 시작하는 constant-arrival-rate 방식으로
60초간 수행했다. 최대 50 VU를 사용했고 같은 조건으로 3회 반복한 뒤 각 지표의
중앙값을 대표값으로 사용했다.

#### 6.5.2. 1 VU 기준 성능

| 데이터 수 | 요청 수 | 처리량 | 평균 | p50 | p95 | p99 | 최대 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 4,293 | 71.53 RPS | 11.99ms | 11.52ms | 14.23ms | 18.92ms | 42.83ms |
| 10,000 | 542 | 9.02 RPS | 109.77ms | 106.71ms | 125.95ms | 177.78ms | 355.26ms |
| 100,000 | 21 | 0.339 RPS | 2.94s | 2.88s | 3.31s | 3.62s | 3.70s |

모든 규모에서 완료된 요청의 검사 성공률은 100%, HTTP 오류율은 0%였고 중단
iteration은 없었다. 그러나 10만 건은 서버 오류가 없어도 사용자 한 명의 검색 응답
중앙값이 2.88초에 이르렀다. H2 common/all 실행시간 중앙값 2.929초와 API p50
2.88초가 유사하므로 전체 API 응답에서 DB 검색 쿼리가 지연의 대부분을 차지한다고
판단했다.

#### 6.5.3. 50 RPS 공식 부하 테스트 대표값

| 데이터 수 | 완료 요청 | 실제 처리량 | 평균 | p50 | p95 | p99 | 최대 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 3,001 | 50.006 RPS | 14.27ms | 12.79ms | 17.69ms | 39.54ms | 241.73ms |
| 10,000 | 3,001 | 49.887 RPS | 181.11ms | 170.03ms | 300.66ms | 515.82ms | 757.07ms |
| 100,000 | 190 | 2.714 RPS | 15.70s | 17.08s | 19.80s | 19.93s | 19.97s |

| 데이터 수 | 검사 성공률 | HTTP 오류율 | dropped iteration | 중단 iteration | 실제 최대 VU |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 100% | 0% | 0 | 0 | 6 |
| 10,000 | 100% | 0% | 0 | 0 | 26 |
| 100,000 | 100% | 0% | 2,791 | 20 | 50 |

1천 건과 1만 건은 목표한 약 50 RPS를 60초 동안 요청 누락 없이 처리했다. 10만 건은
완료된 요청의 응답 내용은 모두 올바르고 HTTP 오류도 없었지만 실제 처리량은 약
2.714 RPS에 그쳤다. 예약된 요청 중 2,791건은 사용할 VU가 없어 시작조차 하지 못했고,
테스트 종료 시 진행 중이던 20건도 중단됐다.

`HTTP 오류율 0%`는 서버가 50 RPS를 처리했다는 뜻이 아니다. 시작되어 완료된 요청이
정상 응답이었다는 뜻이다. constant-arrival-rate 테스트에서는 목표 도착률, 실제
처리량, dropped iteration을 함께 봐야 한다.

#### 6.5.4. 10만 건 3회 상세 결과

| 회차 | 완료 요청 | 처리량 | 평균 | p50 | p95 | p99 | 최대 | dropped | 중단 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1회차 | 160 | 2.285 RPS | 18.44s | 19.36s | 23.08s | 23.13s | 23.17s | 2,814 | 27 |
| 2회차 | 190 | 2.714 RPS | 15.70s | 17.08s | 19.80s | 19.93s | 19.97s | 2,791 | 20 |
| 3회차 | 210 | 3.000 RPS | 14.92s | 16.23s | 17.11s | 17.55s | 17.58s | 2,781 | 10 |

세 회차 모두 최대 50 VU를 사용했지만 목표 50 RPS에 크게 미달했다. VU 한도를 더
늘리면 시작할 수 있는 요청 수는 늘어날 수 있지만, 이미 50개의 동시 요청에서 응답
시간이 15~23초 수준으로 증가했다. 따라서 VU 증가는 느린 검색 쿼리의 근본 해결책이
아니며 DB와 애플리케이션에 더 큰 대기열과 부하를 만들 가능성이 있다.

### 6.6. 문제 원인과 실무적 판단

10만 건 성능 저하를 `JOIN FETCH` 하나의 문제로 단정하지 않았다. 현재 결과는 다음
조건이 결합된 결과다.

1. 검색어 앞에 `%`가 있는 `LIKE '%keyword%'`는 일반적인 B-tree 인덱스로 검색 시작
   위치를 찾기 어렵다.
2. 각 후보 행에서 `LOWER()`를 호출하고 제목과 긴 본문을 문자열 비교한다.
3. 작성자 정보를 한 요청에서 가져오기 위한 조인이 포함된 상태에서 H2가 작성자를
   먼저 읽고 `USER_ID` 인덱스로 게시글을 조인하는 계획을 선택했다.
4. nullable 커서의 `cursor IS NULL OR post_id < cursor` 형태가 H2에서 기본 키 범위
   탐색을 방해했다.
5. 검색 결과가 최대 11건이어도 현재 계획은 조건 평가와 정렬을 위해 전체 게시글에
   가까운 범위를 확인했다.

작성자 조인은 선택된 실행 계획과 비용에 영향을 주었지만, 이를 제거하는 것만으로
`%keyword%` 검색의 구조적 한계가 해결되는 것은 아니다. 반대로 선행 와일드카드만
원인이라고 단정할 수도 없다. 현재 쿼리 형태, 조인 순서, 문자열 연산, 커서 조건 및
H2 옵티마이저의 선택을 함께 개선하고 다시 측정해야 한다.

1천 건과 1만 건에서는 현재 구현이 이번 실험의 목표인 50 RPS를 처리했다. 그러나
10만 건에서는 단일 사용자 p50이 2.88초이고, 50 RPS 조건의 실제 처리량이 약
2.714 RPS, p50이 17.08초, dropped iteration이 2,791건이었다. 정상 응답 여부와
별개로 사용자 경험과 처리 용량 모두 상용 검색 기능으로 사용하기 어려운 수준이다.

따라서 10만 건을 현재 H2와 `LOWER() LIKE '%keyword%'` 구조의 실패 지점으로 판단했다.
같은 방식으로 50만 건을 측정해 더 큰 지연을 확인하는 것은 새로운 판단 근거를 거의
추가하지 않으므로 50만 건 테스트는 중단했다.

### 6.7. 후속 개선 방향

다음 단계에서는 데이터베이스를 PostgreSQL로 이전하고, 동일한 10만 건 데이터와 API
계약 및 부하 조건에서 다음 방식을 비교한다.

1. PostgreSQL 기본 `LIKE '%keyword%'`: DB 변경만으로 실행 계획과 성능이 어떻게
   달라지는지 확인할 기준선
2. `pg_trgm`: 부분 문자열 검색을 유지하면서 GIN 또는 GiST 인덱스를 활용하는 방식
3. PostgreSQL Full Text Search: 토큰 기반 검색의 성능과 검색 결과 특성을 확인하는
   방식

쿼리에서는 첫 페이지와 다음 페이지를 분리해 nullable OR를 제거할 수 있는지,
게시글 ID를 먼저 검색한 뒤 필요한 작성자 정보를 조인하는 2단계 조회가 유리한지,
검색과 정렬에 적절한 인덱스를 사용할 수 있는지도 함께 검토한다.

비교 결과는 응답 시간만 보지 않고 실행 계획, 실제 처리량, dropped iteration,
인덱스 크기, 인덱스 생성 시간, 쓰기 비용 및 검색 결과의 의미 차이를 함께 평가한다.
PostgreSQL 개선 후에도 요구 성능이나 검색 품질을 충족하지 못하거나 검색 기능의 확장
요구가 커지면 Elasticsearch를 별도 후보로 비교한다. 이때는 성능뿐 아니라 DB와 검색
엔진 간 데이터 동기화, 결과 일관성, 장애 대응 및 운영 복잡도까지 포함해 도입 여부를
판단한다.
