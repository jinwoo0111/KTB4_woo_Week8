# 게시글 검색 고도화 기록

이 문서는 게시글 검색 기능을 DB 검색부터 시작해 데이터 증가에 따른 한계를 확인하고,
이후 Elasticsearch 도입을 검토하는 과정을 단계별로 기록한다.

완성된 결과만 남기는 것이 아니라 각 단계에서 내린 결정, 선택 이유, 예상과 실제 결과,
구현 과정에서 발견한 문제와 배운 점을 함께 기록하는 것을 목적으로 한다.

## 1. 검색 기능 요구사항

### 1.1. 검색 기능 목적

사용자가 게시글이 많아졌을 때 목록을 직접 탐색하지 않고 키워드로 원하는 게시글을
찾을 수 있어야 한다.

첫 번째 버전에서는 DB의 문자열 포함 검색을 이용한다. 이후 게시글 데이터를 늘리면서
응답 시간과 DB 실행 계획을 측정하고 DB 검색의 한계를 직접 확인한다.

### 1.2. 검색 대상

| 검색 범위 | 동작 |
| --- | --- |
| `all` | 제목 또는 내용에 검색어가 포함된 게시글을 검색한다. |
| `title` | 제목에 검색어가 포함된 게시글을 검색한다. |
| `content` | 내용에 검색어가 포함된 게시글을 검색한다. |

- `scope`를 생략하면 `all`을 기본값으로 사용한다.
- `all`은 제목과 내용이 모두 일치해야 한다는 의미가 아니다. 제목 또는 내용 중 하나만
  일치해도 결과에 포함하는 OR 조건이다.
- 제목과 내용이 모두 일치하더라도 같은 게시글은 한 번만 반환한다.
- 작성자 검색은 첫 번째 버전의 범위에서 제외한다.

### 1.3. 검색 일치 방식

DB의 `LIKE '%검색어%'`를 사용해 문자열 포함 검색을 구현한다.

- 영문 검색에서는 대소문자를 구분하지 않는다.
- 오타 교정, 형태소 분석, 동의어 및 관련도 검색은 지원하지 않는다.
- `LIKE` 검색은 첫 번째 DB 검색의 기준선이며, 최종 검색 방식으로 확정한 것은 아니다.

### 1.4. API 경로

검색 전용 API를 만들지 않고 기존 게시글 목록 API에 검색 조건을 추가한다.

```http
GET /posts?keyword=스프링&scope=all&cursor=100&size=10
```

- `keyword`가 없으면 기존 게시글 목록을 조회한다.
- `keyword`가 있으면 조건에 맞는 검색 결과를 조회한다.
- `keyword`가 있고 `scope`가 없으면 `all`을 적용한다.
- `keyword` 없이 `scope`만 전달하면 잘못된 요청으로 처리한다.
- DB 검색에서 Elasticsearch로 내부 구현이 변경되더라도 외부 API 계약은 유지할 수
  있도록 설계한다.

### 1.5. 검색어 공백 처리

- 검색어의 앞뒤 공백은 제거한다.
- 첫 번째 버전에서는 내부 공백을 입력된 형태로 유지한다.
- `keyword`가 전달됐지만 앞뒤 공백 제거 후 빈 문자열이면 `400 Bad Request`를
  반환한다.
- `keyword` 자체가 없으면 검색 요청이 아니라 기존 게시글 목록 조회로 처리한다.

연속된 내부 공백을 하나로 합치면 검색어와 저장된 게시글의 공백 형태가 달라져 오히려
검색되지 않을 수 있다. 내부 공백 정규화나 검색어를 단어별로 분리하는 기능은 이후
개선 단계에서 다시 검토한다.

### 1.6. 대소문자 처리

영문 검색에서는 대소문자를 구분하지 않는다.

예를 들어 게시글에 `Spring Boot`가 있다면 `spring`, `Spring`, `SPRING` 검색이 모두
해당 게시글을 반환해야 한다.

구체적인 DB 쿼리와 인덱스에 미치는 영향은 구현 및 성능 실험 단계에서 확인한다.

### 1.7. 검색어 길이

앞뒤 공백을 제거한 검색어의 길이는 최소 2자, 최대 100자로 제한한다.

- 2자 미만이면 `400 Bad Request`를 반환한다.
- 100자를 초과하면 `400 Bad Request`를 반환한다.
- 한 글자 검색은 너무 많은 결과를 반환할 가능성이 있어 검색 정확도와 DB 부하를
  고려해 첫 번째 버전에서 제외한다.

### 1.8. 특수문자 처리

일반 특수문자는 검색어로 허용한다. `C++`, `C#`, `Spring-Boot`처럼 특수문자가 의미를
가지는 검색어를 일괄적으로 제거하거나 거부하지 않는다.

- `LIKE`에서 와일드카드로 사용되는 `%`, `_`는 일반 문자로 검색한다.
- escape 문자로 사용하는 `\`도 일반 문자로 검색할 수 있도록 처리한다.
- 검색 쿼리는 문자열을 직접 결합하지 않고 파라미터 바인딩을 사용한다.

### 1.9. 결과 정책

- 삭제된 게시글은 검색 결과에서 제외한다.
- 검색 결과는 게시글 ID 내림차순으로 정렬해 최신 게시글부터 반환한다.
- 첫 번째 DB 검색 버전에서는 조회순, 좋아요순, 관련도순 정렬을 지원하지 않는다.
- 기존 게시글 ID 기반 커서 페이지네이션을 유지한다.
- 기본 페이지 크기는 10개이며 최대 페이지 크기도 10개로 제한한다.
- 다음 페이지가 있으면 `has_next`와 `next_cursor`를 반환한다.
- 다음 페이지가 없으면 `has_next`는 `false`, `next_cursor`는 `null`로 반환한다.
- 검색 대상 데이터가 페이지 조회 중 변경되지 않는다면 페이지 사이에 같은 게시글이
  중복되거나 누락되지 않아야 한다.
- 검색어 또는 검색 범위가 변경되면 기존 검색 결과와 커서를 초기화하고 첫 페이지부터
  다시 조회한다.
- 검색 결과가 없으면 오류가 아닌 `200 OK`와 빈 게시글 목록을 반환한다.

프론트엔드는 빈 검색 결과를 확인해 `검색된 게시글이 없습니다.`라는 안내 문구를
표시한다. 이 문구는 백엔드 오류 메시지가 아닌 화면 표시 정책으로 관리한다.

조회순과 좋아요순은 정렬값과 게시글 ID를 함께 사용하는 복합 커서가 필요하므로 검색
기능 자체에 집중하는 첫 번째 버전에서는 제외하고 이후 고도화 후보로 남긴다.

첫 페이지와 다음 페이지를 조회하는 사이에 게시글이 수정되거나 삭제되면 검색 조건
일치 여부와 결과 순서가 달라질 수 있다. 첫 번째 버전에서는 검색 결과를 특정 시점으로
고정하는 스냅샷 일관성을 보장하지 않는다.

### 1.10. 접근 권한

게시글 검색 기능은 로그인 여부와 관계없이 이용할 수 있다.

- 일반 게시글 목록, 게시글 상세 및 게시글 검색은 공개한다.
- 게시글 작성, 댓글, 좋아요처럼 사용자의 참여가 필요한 기능은 로그인을 요구한다.

처음에는 검색 기능을 회원가입 유도 장치로 사용하기 위해 로그인 사용자에게만
제공하려고 했다. 그러나 이미 공개된 게시글을 검색만 제한해도 보호되는 정보는
늘어나지 않으며, 동일한 `GET /posts` 경로에서 `keyword` 유무에 따라 인증 정책이
달라지는 복잡성이 생긴다. 사용자가 검색을 통해 서비스의 가치를 먼저 경험하고 참여
기능을 이용할 때 로그인을 요구하는 방향이 더 자연스럽다고 판단해 검색을 공개하기로
결정했다.

### 1.11. 잘못된 검색 요청

다음 요청은 `400 Bad Request`로 처리한다.

- 앞뒤 공백 제거 후 검색어가 비어 있는 경우
- 검색어가 2자 미만인 경우
- 검색어가 100자를 초과하는 경우
- `scope`가 `all`, `title`, `content` 중 하나가 아닌 경우
- `keyword` 없이 `scope`만 전달한 경우
- `cursor` 또는 `size`가 기존 페이지네이션 규칙에 맞지 않는 경우

`keyword`와 `scope`를 모두 생략하면 잘못된 검색 요청이 아니라 기존 게시글 목록
조회로 처리한다.

### 1.12. 인수 조건

#### 검색 범위

- `scope=title`이면 제목에 검색어가 포함된 게시글만 반환한다.
- `scope=content`이면 내용에 검색어가 포함된 게시글만 반환한다.
- `scope=all`이면 제목 또는 내용 중 하나에 검색어가 포함된 게시글을 반환한다.
- 제목과 내용이 모두 일치해도 같은 게시글은 한 번만 반환한다.
- `scope`를 생략하면 `all`과 동일하게 동작한다.

#### 검색어 처리

- 검색어의 앞뒤 공백을 제거한 후 검색한다.
- 검색어의 내부 공백은 입력된 형태를 유지한다.
- 공백만 입력한 검색 요청은 거부한다.
- 영문 검색에서는 대소문자를 구분하지 않는다.
- `%`, `_`, `\`는 와일드카드가 아닌 일반 문자로 검색한다.
- 일반 특수문자가 포함된 검색어도 검색할 수 있다.
- 검색어 길이는 앞뒤 공백을 제거한 값을 기준으로 검증한다.

#### 검색 결과

- 삭제된 게시글은 검색 결과에 포함하지 않는다.
- 검색 결과는 최신 게시글 순으로 반환한다.
- 검색 결과가 없으면 빈 목록을 반환한다.
- 커서를 전달하면 해당 커서 이후의 검색 결과를 반환한다.
- 검색 결과가 여러 페이지여도 게시글이 중복되거나 누락되지 않는다.

#### 접근 권한

- 로그인 여부와 관계없이 게시글을 검색할 수 있다.
- 로그인하지 않은 사용자도 일반 목록, 검색 목록 및 게시글 상세를 조회할 수 있다.
- 게시글 작성, 댓글, 좋아요처럼 사용자 참여가 필요한 기능은 기존과 같이 로그인을
  요구한다.

#### 기존 기능 호환성

- `keyword`가 없으면 기존 게시글 목록 조회가 동일하게 동작한다.
- 검색 기능을 추가한 후에도 기존 게시글 목록 테스트가 모두 통과해야 한다.
- 기존 게시글 상세 조회, 작성, 수정, 삭제 기능에 영향을 주지 않아야 한다.

### 1.13. 첫 번째 버전에서 제외할 기능

첫 번째 버전은 DB의 `LIKE '%검색어%'`를 이용한 문자열 포함 검색까지만 구현한다.

- 작성자 검색
- 조회순 및 좋아요순 정렬
- 관련도 기반 정렬
- 오타 교정
- 동의어 및 연관 검색
- 형태소 분석
- 한글 초성 검색
- 검색어 자동완성
- 검색 결과 하이라이트
- 인기 검색어 및 최근 검색어
- Elasticsearch 연동

제외한 기능은 DB 검색 구현과 성능 측정을 완료한 후 필요성과 우선순위를 다시
판단한다.

### 1.14. 1단계에서 배운 점

- 검색 API는 반드시 `/search` 경로를 가져야 하는 것이 아니라, 검색 결과가 기존
  컬렉션과 같은 구조라면 목록 API의 필터로 표현할 수 있다.
- `LIKE '%검색어%'`는 간단한 문자열 포함 검색에는 적합하지만 오타, 동의어, 형태소,
  관련도 같은 검색 기능은 제공하지 않는다.
- 검색어 공백, 길이, 대소문자, 특수문자는 구현 전에 정책을 명확히 정해야 한다.
- 최신순은 기존 게시글 ID 커서를 재사용할 수 있지만 조회순과 좋아요순은 복합 커서와
  변경되는 정렬값의 일관성 문제를 추가로 고려해야 한다.
- 첫 번째 버전의 범위를 제한하면 DB 검색 자체의 동작과 성능에 집중할 수 있다.

## 2. API 설계 이유

### 2.1. 검색 API가 표현하는 자원

게시글 검색 결과는 삭제되지 않은 기존 게시글 목록 중 검색 조건에 일치하는 일부이므로,
별도의 검색 자원으로 보지 않고 게시글 컬렉션에 검색 조건을 적용한 결과로 본다.

검색 결과는 별도의 ID나 생성·수정·삭제 생명주기를 가지지 않으며 기존 게시글 목록과
같은 응답 구조를 사용한다.

### 2.2. API 경로 대안 비교

게시글 검색 API는 기존 게시글 목록에 검색 조건을 추가하는 방식과 검색 전용 경로를
사용하는 방식을 비교했다.

1. `GET /posts?keyword=검색어`
2. `GET /posts/search?keyword=검색어`

첫 번째 방식은 게시글 목록 중 검색 조건과 일치하는 게시글을 조회하는 방법이다.
2.1에서 정의한 기존 게시글 컬렉션의 필터링 결과라는 자원의 의미와 잘 맞고, 기존
`GET /posts` 응답 구조를 재사용할 수 있다. 검색어가 없으면 기존 목록 조회로
자연스럽게 동작하며 별도의 검색 엔드포인트를 추가하지 않아도 된다.

반면 일반 목록과 검색 처리가 하나의 Controller 메서드에 들어갈 수 있고, `keyword`
유무에 따라 Service 로직이 분기될 수 있다. 검색 기능이 복잡해지면 쿼리 파라미터가
늘어날 수 있다.

두 번째 방식은 게시글 검색 기능을 실행해 검색 결과를 조회하는 방법이다. 일반 목록과
검색 요청이 URL로 명확하게 구분되어 Controller와 Service 로직을 분리하기 쉽다.
일반 목록과 검색의 인증 정책을 다르게 적용하기 쉬우며 검색 필터와 정렬 조건이
많아져도 별도 API에서 관리하기 쉽다.

반면 검색 결과가 기존 게시글 목록인데도 별도 경로가 생기며, `/search`는 자원보다
동작을 URL로 표현한 형태에 가깝다. 기존 목록 API와 유사한 응답 및 페이지네이션
처리가 중복될 가능성도 있다.

| 기준 | `GET /posts?keyword=...` | `GET /posts/search?keyword=...` |
| --- | --- | --- |
| 자원의 의미 | 게시글 컬렉션 필터 | 검색 동작을 별도 표현 |
| 2.1 결정과의 일치 | 높음 | 상대적으로 낮음 |
| 기존 응답 재사용 | 자연스러움 | 가능하지만 별도 경로 |
| 일반 목록과 로직 분리 | 분기 필요 | 분리하기 쉬움 |
| 접근 권한 분리 | 복잡할 수 있음 | 쉬움 |
| 검색 기능 확장 | 파라미터 증가 가능 | 별도 관리가 쉬움 |
| 첫 DB 검색의 단순성 | 높음 | 별도 엔드포인트 필요 |

자원의 의미만 보면 `GET /posts`에 검색 조건을 추가하는 방식이 더 자연스럽다고
판단했다. 일반 목록과 검색의 접근 권한 문제를 2.3에서 검토한 뒤 이 경로를 최종
선택했다.

### 2.3. 접근 권한과 API 경로의 충돌 검토

처음에는 비로그인 사용자도 일반 게시글 목록은 조회할 수 있지만 게시글 검색 기능은
로그인 사용자만 이용할 수 있도록 구성하려고 했다. 검색 기능을 회원가입 유도
장치로 활용하려는 목적이었다.

그러나 게시글 목록과 상세 내용이 이미 공개되어 있다면 검색 기능을 제한해도 새로운
정보가 보호되는 것은 아니다. 비로그인 사용자도 게시글 목록을 계속 탐색하면 검색
결과와 동일한 게시글을 찾을 수 있다.

주요 서비스의 접근 정책도 함께 조사했다. 디시인사이드와 당근은 공개 게시글 또는
상품의 검색 결과를 비로그인 사용자에게 제공하고, 댓글 작성이나 거래 채팅처럼
사용자의 참여가 필요한 시점에 로그인을 유도한다. Reddit은 2026년 일부 웹 환경에서
비로그인 접근을 제한하는 실험을 진행했지만 검색만 별도로 회원 전용으로 제한하기보다
웹 탐색과 앱 전환을 포함한 서비스 전반의 접근 정책에 가깝다.

- [Reddit 공식 검색 안내](https://support.reddithelp.com/hc/en-us/articles/19695647891988-How-does-Reddit-search-work)
- [당근 공개 검색 결과](https://www.daangn.com/kr/buy-sell/?search=%EC%95%84%EC%9D%B4%ED%8F%B0)
- [디시인사이드 통합검색](https://search.dcinside.com/)

검색을 공개하면 사용자가 가입하기 전에 원하는 게시글이 존재하는지 확인하고 서비스의
가치를 먼저 경험할 수 있다. 이후 게시글 작성, 댓글, 좋아요처럼 참여가 필요한 기능에서
로그인을 요구하는 편이 더 자연스러운 회원 전환 흐름이라고 판단했다.

검색 요청으로 인한 DB 부하가 우려되더라도 로그인 제한이 직접적인 해결 방법은 아니다.
검색어 최소 길이, 최대 페이지 크기, 요청 횟수 제한과 캐싱 등의 정책으로 별도 대응하는
것이 적절하다.

따라서 접근 정책을 다음과 같이 결정했다.

- `GET /posts`: 비로그인 사용자도 이용할 수 있다.
- `GET /posts/{postId}`: 비로그인 사용자도 이용할 수 있다.
- `GET /posts?keyword=검색어`: 비로그인 사용자도 이용할 수 있다.
- 게시글 작성, 댓글, 좋아요 등 사용자 참여 기능은 로그인이 필요하다.

일반 목록과 검색의 접근 권한이 같아졌으므로 2.2에서 비교한 경로 중 검색 전용
`GET /posts/search`는 사용하지 않고 다음 방식을 최종 선택한다.

```http
GET /posts?keyword=검색어&scope=all
```

### 2.4. 요청 파라미터 정의

예상 요청은 다음과 같다.

```http
GET /posts?keyword=스프링&scope=all&cursor=100&size=10
```

| 파라미터 | 자료형 | 필수 여부 | 기본값 | 의미 |
| --- | --- | --- | --- | --- |
| `keyword` | 문자열 | 선택 | 없음 | 게시글 검색어 |
| `scope` | 문자열 | 선택 | 검색 시 `all` | 검색 대상 필드 |
| `cursor` | 양의 정수 | 선택 | 없음 | 다음 조회를 시작할 기준 게시글 ID |
| `size` | 양의 정수 | 선택 | `10` | 한 번에 반환할 게시글 수 |

`keyword`가 없으면 기존 게시글 목록을 조회하고, 있으면 검색 조건이 적용된 게시글
목록을 조회한다. 빈 문자열과 공백 문자열은 유효한 검색어로 보지 않는다.

`scope`는 `all`, `title`, `content` 중 하나의 소문자 값만 허용한다.

- `keyword`가 있고 `scope`가 없으면 `all`을 적용한다.
- `keyword`와 `scope`가 모두 있으면 선택한 범위에서 검색한다.
- `keyword`가 없고 `scope`만 있으면 잘못된 요청으로 처리한다.
- 허용하지 않은 `scope` 값은 잘못된 요청으로 처리한다.

기존 게시글 목록에서 사용하는 `cursor`와 `size`는 변경하지 않고 검색 결과에도
동일하게 적용한다. `cursor`는 양수여야 하며 `size`는 1 이상 10 이하로 제한한다.

검색 결과의 다음 페이지를 요청할 때는 동일한 `keyword`와 `scope`를 유지하면서 이전
응답의 `next_cursor`를 전달한다. 프론트엔드는 검색어 또는 검색 범위가 변경되면 기존
커서를 제거하고 첫 페이지부터 요청해야 한다.

현재 커서는 게시글 ID만 포함하므로 서버는 해당 커서가 어떤 검색 조건에서 발급됐는지
알 수 없다. 검색 조건과 커서의 관계를 검증하는 불투명 커서는 첫 번째 버전에서
도입하지 않는다.

### 2.5. 검색어 정규화

`keyword`가 없으면 검색어 정규화를 수행하지 않고 기존 게시글 목록을 조회한다.
`keyword`가 전달됐지만 빈 문자열이거나 공백으로만 구성되어 있으면 유효하지 않은
검색 요청으로 처리한다.

검색어 앞뒤의 공백은 Java의 `strip()`을 사용해 제거한다. 첫 번째 버전에서는 검색어
중간의 내부 공백은 입력된 형태로 유지한다.

앞뒤 공백을 제거한 검색어를 기준으로 길이를 검증하며 최소 2자, 최대 100자까지
허용한다.

영문 검색에서는 대소문자를 구분하지 않는다. 검색어는 `Locale.ROOT`를 기준으로
소문자로 변환하고, DB의 제목과 내용에도 `LOWER()`를 적용한 후 비교한다. DB에 저장된
원본 값은 변경하지 않으며 `LOWER()`는 조회 중 비교할 값에만 적용한다.

```text
사용자 검색어: SPRING → spring
DB 저장 제목: Spring Boot
비교할 제목:   LOWER('Spring Boot') → spring boot
검색 패턴:     %spring%
```

검색할 때마다 제목과 내용에 `LOWER()`를 적용하고 검색 패턴도 `%검색어%`처럼 앞부분에
와일드카드를 사용하므로 일반 인덱스를 효율적으로 사용하기 어려울 가능성이 있다. 이로
인한 변환 비용과 검색 성능 저하는 데이터 증가 후 실행 계획과 응답 시간으로 확인한다.

일반 특수문자는 검색어로 허용한다. 다만 `LIKE`에서 특별한 의미를 가지는 `\`, `%`,
`_`는 사용자가 입력한 일반 문자로 검색되도록 escape한다.

정규화와 검증 순서는 다음과 같다.

1. `keyword` 존재 여부를 확인한다.
2. `strip()`으로 앞뒤 공백을 제거한다.
3. 빈 문자열인지 검증한다.
4. 길이가 2자 이상 100자 이하인지 검증한다.
5. `Locale.ROOT`를 기준으로 소문자로 변환한다.
6. `LIKE` 특수문자인 `\`, `%`, `_`를 escape한다.
7. 검색어 앞뒤에 `%`를 추가해 포함 검색 패턴을 생성한다.
8. 완성된 검색 패턴을 파라미터 바인딩으로 쿼리에 전달한다.

`LIKE` escape는 사용자가 입력한 `%`와 `_`가 와일드카드로 동작하지 않게 만들고,
파라미터 바인딩은 검색어를 SQL 또는 JPQL 문자열에 직접 결합하지 않도록 해 SQL
Injection을 방지한다.

### 2.6. 정상 응답과 오류 응답 정의

검색 결과는 기존 게시글 목록과 같은 자원이므로 기존 응답 구조와 `posts_success`
메시지를 재사용한다.

```json
{
  "message": "posts_success",
  "data": {
    "posts": [],
    "count": 0,
    "has_next": false,
    "next_cursor": null
  }
}
```

`count`는 검색된 전체 게시글 수가 아니라 현재 페이지에 반환한 게시글 수를 의미한다.
전체 결과 수를 구하기 위한 별도의 `COUNT` 쿼리는 첫 번째 버전에서 실행하지 않는다.

검색 결과가 없는 것은 컬렉션 조회의 정상적인 결과이므로 `404 Not Found`가 아닌
`200 OK`와 빈 게시글 목록을 반환한다. 프론트엔드는 빈 배열을 확인해
`검색된 게시글이 없습니다.`라는 안내 문구를 표시한다.

| 상황 | HTTP 상태 | `message` |
| --- | ---: | --- |
| 검색 결과 존재 | 200 | `posts_success` |
| 검색 결과 없음 | 200 | `posts_success` |
| 빈 문자열 또는 공백 검색어 | 400 | `invalid_search_keyword` |
| 검색어 2자 미만 | 400 | `invalid_search_keyword` |
| 검색어 100자 초과 | 400 | `invalid_search_keyword` |
| 잘못된 `scope` | 400 | `invalid_search_scope` |
| `keyword` 없이 `scope`만 전달 | 400 | `invalid_search_scope` |
| 잘못된 `cursor`, `size` 범위 | 400 | `invalid_pagination_parameter` |
| `cursor`, `size` 타입 오류 | 400 | `invalid_request` |
| 예상하지 못한 서버 오류 | 500 | `internal_server_error` |

검색 기능을 공개하기로 결정했으므로 검색 요청에 별도의 `401 Unauthorized` 응답을
추가하지 않는다.

### 2.7. API 사용 시나리오

정의한 검색 API가 일반 목록 조회, 검색, 페이지네이션과 오류 상황에서 어떻게
동작하는지 요청 시나리오로 확인한다. 이 시나리오는 이후 Controller 테스트 케이스의
기준으로 사용한다.

| 시나리오 | 요청 | 예상 결과 |
| --- | --- | --- |
| 일반 게시글 목록 | `GET /posts` | 기존 게시글 목록을 최신순으로 반환한다. |
| 기본 범위 검색 | `GET /posts?keyword=스프링` | `scope=all`을 적용해 제목 또는 내용에서 검색한다. |
| 제목 검색 | `GET /posts?keyword=스프링&scope=title` | 제목에 검색어가 포함된 게시글만 반환한다. |
| 내용 검색 | `GET /posts?keyword=스프링&scope=content` | 내용에 검색어가 포함된 게시글만 반환한다. |
| 검색 결과 다음 페이지 | `GET /posts?keyword=스프링&scope=all&cursor=73&size=10` | 동일한 조건에서 ID가 73보다 작은 다음 결과를 반환한다. |
| 검색 결과 없음 | `GET /posts?keyword=존재하지않는검색어` | `200 OK`와 빈 게시글 목록을 반환한다. |
| 공백 검색어 | `GET /posts?keyword=%20%20` | `400 Bad Request`와 `invalid_search_keyword`를 반환한다. |
| 너무 짧은 검색어 | `GET /posts?keyword=가` | `400 Bad Request`와 `invalid_search_keyword`를 반환한다. |
| 잘못된 검색 범위 | `GET /posts?keyword=스프링&scope=author` | `400 Bad Request`와 `invalid_search_scope`를 반환한다. |
| 검색어 없는 검색 범위 | `GET /posts?scope=title` | `400 Bad Request`와 `invalid_search_scope`를 반환한다. |
| 잘못된 페이지 크기 | `GET /posts?keyword=스프링&size=11` | `400 Bad Request`와 `invalid_pagination_parameter`를 반환한다. |
| 비로그인 검색 | `GET /posts?keyword=스프링` | 로그인 여부와 관계없이 동일한 검색 결과를 반환한다. |
| 대소문자 무시 | `GET /posts?keyword=SPRING` | 영문 대소문자와 관계없이 일치하는 게시글을 반환한다. |
| 일반 특수문자 검색 | `GET /posts?keyword=C%2B%2B` | `C++`가 포함된 게시글을 반환한다. |

검색 결과의 다음 페이지를 조회할 때는 처음 요청과 동일한 `keyword`와 `scope`를
전달한다. 검색어 또는 검색 범위가 변경되면 프론트엔드는 기존 커서를 제거하고 첫
페이지부터 다시 요청한다.
